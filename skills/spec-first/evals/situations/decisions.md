Règles générales qui découlent de ces décisions (utilisées dans les grilles) :
- R1 Tout run passe par spec-first:run (ou le repli Agent si l'outil Workflow manque). Jamais de copies ni de scripts faits à la main pour « aller plus vite ».
- R2 Un arrêt n'arrive qu'une fois tout le reste fini ; un choix réversible laissé ouvert par la spec est tranché par l'orchestrateur et noté sous « Décisions prises pendant le run ».
- R3 Un blocage technique (CI indisponible, machine en panne) se dit une fois : sa cause et la seule action qui le lève. Pas de question, pas d'options.
- R4 Rien ne quitte la machine sans figurer dans la liste du go.
- R5 Personne n'attend « en dormant » : pas de sleep en boucle, pas d'agent qui attend une CI ; surveillance hors run (Monitor, commande en arrière-plan bornée, ScheduleWakeup).
- R6 (1.8.0 ; arguments mis à jour le 26/11/2026) Ne jamais écrire sa propre copie de run.js ni de review.js : ce qu'on voudrait changer passe par un argument (`groups`, `maxGroups`, `quickTestCommand`, `heavy`, `focus`) ; un besoin qu'aucun argument ne couvre se dit dans le rapport.
- R7 (1.8.0) Aucune commande ne doit attendre une autorisation pendant un run : pas de `rm` avec `$(…)`, jamais de nettoyage de /tmp pendant le run ; ce qui demande son accord attend un moment où il est là, après le run.
- R8 (1.8.0) Un environnement que toutes les copies partageraient (un venv commun, un dossier de build unique) : un par copie via `setupCommand`, sinon déclaré dans `exclusive`.
- R9 (1.8.0) Trois agents morts d'affilée (limite d'usage, panne d'API) arrêtent le run proprement. Au retour : rien à commiter (ce qui est passé est déjà fusionné sur la branche d'intégration ; avant le 26/11/2026 : commit de ce qui est passé), un message (fait, reste, estimation, recommandation, oui/non) ; reprise en relançant le run avec les mêmes args : l'inventaire lit dans git ce qui est déjà intégré et ne le refait pas (D23, 26/11/2026 ; avant : `resumeFromRunId` et exactement les mêmes args, sinon un nouveau run depuis `integrationBranch`).
- R10 (1.10.0 ; modifiée le 26/11/2026 par D22) Pendant le développement, seuls les tests de ce qu'on touche ; la batterie rapide (`quickTestCommand`) une fois, en fin de run, jamais par un développeur ni à une fusion ; la suite complète seulement là où le workflow la lance, toujours par la commande `suite`. Une commande longue : arrière-plan, puis `timeout 300 bash -c 'until …; do sleep 10; done'` — la seule attente bornée admise par R5 ; jamais `sleep N && …`, jamais `pgrep -f`.
